\chapter{What I Must Know Before Putting This Project on My Resume}
\label{ch:resume}

This chapter turns the whole report into a checklist for the résumé and the interview. It separates what you can claim from what you cannot, gives wording that survives scrutiny, and lists the questions you are most likely to be asked.

\section{The project in one honest paragraph}

VidyaRAG is a carefully instrumented retrieval-augmented study assistant over two open biology textbooks, with validated page-level citations, a claim-level self-check that turns unsupported or refusing drafts into an explicit abstention, regex injection guards, and an evaluation harness that ablates each component against a frozen baseline. It is deployed as a public demo and packaged as an API with CI. It is a portfolio-scale system: 3,608 passages, a 58-question gold set, single evaluation runs, free-tier models, and several measurement defects --- found by the analysis behind this report, and since fixed, with the retracted numbers stated rather than quietly replaced (Appendix~\ref{app:fixes}).

\section{Résumé bullets you can defend}

\begin{recommended}[wording]
\begin{itemize}
  \item \textbf{System.} Built VidyaRAG, a retrieval-augmented study assistant over two OpenStax textbooks (3,608 passages): local BGE embeddings in Qdrant, cross-encoder reranking, Gemini generation with validated page-level citations, and a claim-level self-check that abstains with a fixed, citation-free response when passages do not support an answer.
  \item \textbf{Evaluation.} Designed an ablation harness (58-question gold set; RAGAS, deterministic retrieval and abstention metrics; frozen baseline): reranking raised recall of gold passages in the prompt from 0.880 to 0.913 and MRR from 0.770 to 0.830; query decomposition was measured and rejected after multi-hop context recall fell from 0.861 to 0.778.
  \item \textbf{Engineering.} Shipped a FastAPI service, a CLI and a Gradio demo on Hugging Face Spaces; Docker image built and health-checked in GitHub Actions; 400+ hermetic tests on Python 3.10 and 3.11 with secret scanning.
  \item \textbf{Only after fixing and re-measuring.} Audited the evaluation pipeline and fixed a truncated LLM judge that had masked baseline refusals, double-counted latency and unrecorded grading tokens; re-measured all profiles.
\end{itemize}
\end{recommended}

\section{The fifteen questions most likely to be asked}

\begin{enumerate}
  \item \textbf{Walk me through the architecture.} Use the 3-minute version (Chapter~\ref{ch:explaining}).
  \item \textbf{Why RAG instead of fine-tuning?} Traceability to pages and the ability to abstain; fine-tuned knowledge cannot cite a source.
  \item \textbf{How do you stop hallucinated citations?} Numbered markers; any marker outside the supplied passages is removed; tests cover grouped and invented markers.
  \item \textbf{How does the self-check work, and does it help?} Claims graded against passages, a refusal flag, a policy with a bounded retry. It standardises and enforces abstention; it did not improve answer quality like for like.
  \item \textbf{How did you evaluate?} Frozen baseline, one change per profile, 58 questions, deterministic retrieval metrics plus RAGAS plus abstention metrics, a 10\% validity rule.
  \item \textbf{What improved, by how much?} Reranking: 0.880 $\rightarrow$ 0.913 recall@context, 0.770 $\rightarrow$ 0.830 MRR, with pool recall unchanged as predicted.
  \item \textbf{What didn't work?} Decomposition, and why: rank fusion favours consensus passages.
  \item \textbf{How do you know it isn't noise?} Retrieval metrics are exact; model-judged metrics move about $\pm$0.05 between runs, so smaller differences are not claimed.
  \item \textbf{Hardest bug?} The tokenizer mismatch that silently truncated chunks, or the five Docker defects exposed by actually running the container --- or the truncated judge, once fixed.
  \item \textbf{Limitations?} Two textbooks, definitional questions, multi-hop, small gold set, regex guards, CPU reranking, free-tier limits.
  \item \textbf{How would you scale it?} Qdrant server with an approximate index, fewer rerank candidates or a smaller model, caching, model warm-up, rate limiting, asynchronous grading.
  \item \textbf{How do you handle prompt injection?} Screen questions before any work and passages before the prompt; be clear that regex guards are shallow and that grounding limits the damage.
  \item \textbf{Latency and cost?} About a second for the baseline, about two more for reranking, grading dominates the self-check; the reported 22 seconds double-counts, and cost omits grading.
  \item \textbf{Why these technologies?} Chapter~\ref{ch:why}.
  \item \textbf{What would you do next?} Fix the measurement defects and re-run, add integration tests, per-term glossary chunks, diversity-aware multi-hop context, a larger gold set with repeated runs.
\end{enumerate}

\section{Before each interview}

\begin{itemize}
  \item Open the live demo a few minutes early: the first request may load or download models, and the free tier can return transient errors. Keep a local run or screenshots as a fallback.
  \item Decide, finding by finding, whether you have fixed it; rehearse how you will describe each (Chapter~\ref{ch:findings}).
  \item Rehearse the 30-second, 1-minute and 3-minute versions aloud.
  \item Be ready to open \code{pipeline.py}, \code{correct/policy.py}, \code{generate/citations.py}, \code{evaluation/retrieval.py} and \code{evaluation/abstention.py}.
  \item Keep the results table (Chapter~\ref{ch:results}) on one page.
  \item Re-run \code{uv run pytest -m "not costly"} so you can say the suite passes today.
\end{itemize}
