\chapter{Master Flows}
\label{ch:flows}

The previous chapters followed one component at a time. This chapter puts them back together in four views: how data moves and where it is stored, how one query executes, how each process starts, and what happens when something fails.

\section{Startup flows}
\label{sec:startup}

\begin{longtable}{@{}>{\raggedright\arraybackslash}p{2.6cm}>{\raggedright\arraybackslash}p{13.2cm}@{}}
\toprule
\textbf{Process} & \textbf{What happens, in order}\\
\midrule
\endhead
HTTP API (uvicorn) & Import \code{vidyarag.api.main} $\rightarrow$ \code{create_app()} registers the \code{/v1} router $\rightarrow$ server starts the \code{lifespan} context: \code{Settings()} reads environment and \code{.env}; structlog is configured; \code{build_pipeline} loads the profile and calls \code{build_client}, which opens the embedded index and takes its lock $\rightarrow$ \code{api.startup} is logged $\rightarrow$ requests are served. The embedding model, the cross-encoder and the Gemini client are \emph{not} loaded yet: each is created on first use \ev{src/vidyarag/llm/provider.py:33-47}, \ev{src/vidyarag/retrieve/rerank.py:31-41}, \ev{src/vidyarag/pipeline.py:72-82}. On shutdown the pipeline closes and releases the lock.\\
Docker container & The same as the API, run by \code{CMD}. The image contains no model weights, so the first query in a fresh container downloads them into \code{FASTEMBED_CACHE_PATH}. The \code{HEALTHCHECK} (every 30\,s after a 60\,s start period) calls \code{/v1/health}, which touches only Qdrant \ev{Dockerfile:59-103}.\\
Gradio demo & \code{python app.py} imports Gradio and the package $\rightarrow$ on a Space, declares the unused \code{@spaces.GPU} function $\rightarrow$ \code{build_ui()} $\rightarrow$ \code{queue(max_size=16).launch(...)}. The pipeline, the index lock and all models are created by the first \code{ask} \ev{app/app.py:68-92, 197-208}.\\
Hugging Face Space & The builder installs \code{requirements.txt} plus Gradio at \code{sdk_version} 5.50.0 on Python 3.10 $\rightarrow$ runs \code{app.py}, whose first lines (spliced in by the deploy script) put \code{src/} on \code{sys.path} $\rightarrow$ ZeroGPU finds the decorated function and starts the container $\rightarrow$ as for the demo. The index is part of the Space's files.\\
CLI command & \code{Settings()} and \code{load_pipeline_config} run inside each command. \code{ask} builds a \code{Pipeline}, answers one question and closes it; \code{ingest} and \code{health} build a client directly. Every invocation pays the model loading again.\\
\bottomrule
\end{longtable}

\begin{inferred}[a consequence of lazy loading]
A container or Space can report healthy long before it can answer quickly. The first question after a start pays for model downloads or loading --- measured on the development machine at between about 5 and 24 seconds for loading alone, depending on the machine's state --- and a first question in a fresh container also pays for the downloads. The committed evaluation runs show the same effect: in each of the \code{rerank}, \code{corrective} and \code{guarded} runs, one of the slowest questions is the first one asked (Chapter~\ref{ch:performance}).
\end{inferred}

\subsection{Failures outside a single query}

\begin{longtable}{@{}>{\raggedright\arraybackslash}p{4.4cm}>{\raggedright\arraybackslash}p{3.4cm}>{\raggedright\arraybackslash}p{7.8cm}@{}}
\toprule
\textbf{Failure} & \textbf{Detected in} & \textbf{Result}\\
\midrule
\endhead
No \code{GOOGLE_API_KEY} & \code{get_gemini_client}, at first model use & \code{ValueError} naming the AI Studio URL: API 503, CLI \enquote{FAIL} with exit code 1, demo error message. Ingestion and \code{/v1/search} are unaffected.\\
Index already opened by another process & \code{build_client} (Qdrant) & The second process fails, for example \enquote{already accessed by another instance of Qdrant client}. This is why the container health check asks the server over HTTP.\\
Unknown profile, misspelt key, \code{use_hybrid: true} & \code{load_pipeline_config} & Start-up error with a specific message (Section~\ref{sec:config-loading}).\\
Server or cloud mode without a URL & \code{Settings} validator & Start-up error.\\
Embedding width differs from the collection & \code{ensure_collection} & \code{ValueError} advising \code{--recreate} or another collection.\\
PDF without an outline & \code{extract_pages} & \code{ValueError}: citations cannot be derived.\\
Download interrupted & \code{_stream_to_part} & Partial \code{.part} file kept; the next run resumes with a \code{Range} request; a stale partial is discarded after a 416.\\
Evaluation dependencies missing & \code{check_grading_dependencies} & \code{RuntimeError} before any answer is generated.\\
Generation failure during evaluation & \code{_answer_one} & Up to 3 attempts with 45 and 90 second waits for transient errors; otherwise the question is recorded as failed. More than 10\% failed makes the run invalid and its metrics are withheld.\\
RAGAS metric failure & \code{MetricSuite._score_one} & Up to 5 attempts with linear back-off; then the score is \code{None} with the error recorded, and averages skip it.\\
Abstention judge failure & \code{judge_abstention} & Returns \code{False}. With the shipped 5-token limit it returns \code{False} even on success (Section~\ref{sec:judge-bug}).\\
\bottomrule
\end{longtable}

\begin{keyidea}[the pattern across all these flows]
The code is consistently strict at configuration and data boundaries --- invalid settings, a wrong vector width, a missing outline all stop the process with a specific message --- and consistently lenient at model-call boundaries: decomposition failures fall back to plain retrieval, grading failures accept the draft, judge failures count as \enquote{answered}. Each lenient choice is documented and defensible on its own. Together they mean that model outages degrade the system quietly rather than loudly, and three of the defects in this report (Sections~\ref{sec:judge-bug}, \ref{sec:trace-failopen} and~\ref{sec:latency-bug}) sit exactly on that seam.
\end{keyidea}
